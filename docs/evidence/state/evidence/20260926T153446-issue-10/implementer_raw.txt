Looking at this:

1. **Root cause:** `_read_body` coerces a missing/empty `Content-Length` to 0, reads zero bytes, and `do_POST` then misreports `400 invalid JSON body` even though the body was never read.

2. **Fix:** In `do_POST`, before parsing the body, check the raw `Content-Length` header value. If absent (`None`) or empty/whitespace-only (`''` — same code path as absent per `int(v or 0)`), respond `411 {"error": "Content-Length required"}` per RFC 7230 §3.3.3. The check goes after the `/paste` path check so 404 routing is unchanged, and only touches POST — GET handlers never call `_read_body`, so criterion 3 is satisfied without touching `do_GET`.

3. **No regression:** Any POST with a present, parseable `Content-Length` skips the new branch entirely and hits the original `json.loads` path, so 201/400 behavior is byte-identical. Malformed header *values* (non-numeric) stay out of scope per the issue (parked as #7) — the check only tests for absence/emptiness.

4. **Tests:** New file `paste_content_length_test.py` covering:
   - Empty `Content-Length` header via `http.client` with explicit header suppression (auto length skipped since caller supplies `Content-Length`, empty value goes on the wire verbatim) → 411 + fragment.
   - Truly absent header via raw socket with a valid JSON body sent anyway → 411 (server responds without reading; safe, no hang).
   - Explicit correct `Content-Length` via `http.client` → 201 with `"id"` (criterion 2).
   - GET `/health` without any `Content-Length` → 200 (criterion 3).

5. **Client/server interplay for the 411 path:** the client sends the body bytes the server never reads; the server responds 411 and closes, and the test closes the connection, so no deadlock. Timeouts set defensively.
