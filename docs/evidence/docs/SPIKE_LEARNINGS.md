## L-000: model split — hostile implementer by design

## L-001: gateway model ids carry no effort suffixes
- What happened: smoke test (2026-09-24, factory-docs/SURPLUS_GATEWAY_SMOKE.md) showed exact live ids `deepseek-v4.1-flash` and `glm-5.3-flash`; `:high`-style suffixes are not part of ids on this gateway.
- Why: gateway convention differs from other aggregators; a suffixed id 404s with `no_sellers_for_model`.
- What changes in the product build: settings.py carries bare ids; 404 `no_sellers_for_model` classified PERMANENT (never retried) in agent.py.
- Evidence: SURPLUS_GATEWAY_SMOKE.md §1, §5; src/settings.py:8-9.

## L-002: reasoning models eat the token budget
- What happened: deepseek-v4.1-flash with `max_tokens: 16` returned `content: null`, `finish_reason: "length"` — reasoning consumed the budget (smoke test §2).
- Why: both target models are reasoning models; `reasoning_content` is separate from `content`.
- What changes in the product build: agent.py sets max_tokens ≥ 512, reads `content` only, and treats null-content `length` as retryable with doubled max_tokens (never accepts a null content as valid).
- Evidence: SURPLUS_GATEWAY_SMOKE.md §2; src/agent.py chat().

## L-003: agent streaming parse — buffer once, not per chunk
- What happened: SSE chunks carry `delta.content` after `reasoning_content` deltas; usage (with cost in USD) arrives in-stream before `[DONE]`.
- Why: per-chunk re-parsing wastes work and risks partial-JSON errors.
- What changes in the product build: agent.py appends raw SSE lines to a buffer and parses once at end (parse_stream); no finish_reason in the buffer = transient, retried once.
- Evidence: SURPLUS_GATEWAY_SMOKE.md §3; tests/fixtures/sse_stream.txt.

## L-007: extractor false reds — the instrument rejected valid prefix-less diffs
- What happened: two Day-4 attempts (issue-9 run 20260926T143357, issue-10 run 20260926T153446) emitted COMPLETE, valid diffs with prefix-less headers (`--- app.py` / `+++ app.py`, git's p-value guess handles p=0), but extract_diff's filter (`"--- a/" in b or "+++ b/" in b`) rejected both blocks, recording gate=diff-extraction, caught_confabulation="model produced no diff despite claiming to implement". The model produced a valid diff; the instrument dropped it.
- Why: a gate's filter must accept every format `git apply` accepts, not just the convention git writes. Also: git's p-value guess is sticky for the whole apply run, so a patch mixing prefix-less and prefixed sections can misparse the later file — extract_diff now normalizes every `---`/`+++` path to the a/ b/ form (leaving /dev/null) before joining blocks. Separately, the crash record dropped CalledProcessError.stderr, which is why the Day-4 gh crash was undiagnosable from artifacts; and the supervisor could report DRAIN while an issue sat with an open PR and a retry disposition (false clean exit) — it now emits BLOCKED and exits nonzero.
- What changes in the product build: (1) extract_diff accepts any fenced block containing both a `--- ` and a `+++ ` header line (or `diff --git`), normalizes paths; (2) crash finish records stderr (decoded, trimmed); (3) supervisor BLOCKED:<issues> instead of DRAIN when a recorded issue has a non-terminal disposition at idle, main exits 1. Misattribution inflates the headline caught-confabulation metric — the instrument's false reds must be replayed and reclassified before quoting that number.
- Evidence: apply-replay of both fixed-extractor patches: extracted (2963 / 3966 bytes), `git apply --check` clean (plain tier) at BOTH bases bf9ca06 (pre-#8) and e6b3db4 (current main). Corrected Day-4 tally: issue-9 = 2 genuine review-rejects + 1 instrument false-red; issue-10 = 1 genuine review-reject + 1 genuine verify-fail + 1 instrument false-red; caught-confabulation count drops 6 → 4. Fix commit dc84d4d3b7ea (factory-spike).

## L-008: git apply exits 0 on silently-dropped header-less sections — apply gates need a declared-vs-applied post-condition
- What happened: three Day-4 attempts (142715, 143026, 152543) emitted diffs mixing a well-formed app.py hunk with a new-file section (`--- /dev/null` / `+++ b/*_test.py`) whose body lines lacked the `@@ -0,0 +1,N @@` hunk header. `git apply` applied the hunk and silently dropped the new-file section while exiting 0; the reviewer then rejected the incomplete artifact it was handed, recording the failures under gate=review. With a dropped *implementation* file the same hole manufactures a false green: the partial patch passes diff-apply and is verified as if complete.
- Why: an apply gate's success condition cannot be "exit code 0" — git apply can succeed while applying strictly less than the patch declares. The gate must assert the diff's DECLARED file set (parsed `---`/`+++` pairs, skipping /dev/null) equals the ACTUALLY-applied file set (`git status --porcelain` post-apply) on every successful tier, and fail loudly (new outcome `apply_incomplete`) with both sets recorded in run evidence.
- What changes in the product build: (1) apply_diff post-condition declared == applied, apply_incomplete outcome, never proceed to review/verify on mismatch; (2) auto-repair of malformed diffs deliberately out of scope — emitting them is a genuine model failure the gate must catch, not fix; (3) malformed-diff model failures now count correctly under the apply gate instead of inflating review-rejects.
- Evidence: [redacted-host] evidence replay of 142715 claimed.diff vs applied.diff (test file absent); regression test test_headerless_new_file_section_fails_loudly (tests/test_lap_diff.py); fix commit df0d5a1d17f6 (factory-spike); DAY4_REPORT.md corrected tally.

## L-009: claim files of finished laps deadlock the queue after any supervisor restart — reconcile must actually run
- What happened: main() wires `reconcile` to a no-op lambda (supervisor.py), so a claim file left by a lap that ended between two supervisor restarts blocks dispatch forever: claim_next skips an issue whose claim file exists and is not stale, and staleness is measured against LAP_WALLCLOCK_LIMIT_S (3h). On Day-5 the first #12 crash left state/claims/issue-12.json while state["lap"] went null → the supervisor looped BLOCKED and exited; the queue only moved after the operator deleted the claim file by hand. A second variant: after a park, a supervisor restarted before the state file settled re-dispatched the parked issue, inflating #10's retries from 3 to 6.
- Why: external liveness was designed as "heartbeat file + pid probe", but claim files are a THIRD liveness artifact and nothing reaps them. A claim whose issue has a terminal lap-result.json (outcome != running) is by definition dead — the reconcile hook exists for exactly this and must reap: (1) claims with a terminal result for the same issue, (2) claims for issues whose durable disposition is parked/merged. Bonus: BLOCKED-on-terminal-issue should read GitHub state (issue closed = done, disposition should be upgraded to merged) instead of exiting.
- What changes in the product build: reconcile(dep) reaps dead claims per the rules above on every tick; supervisor restart path asserts state["lap"] is either heartbeat-alive or reaped before dispatching anything.
- Evidence: [redacted-host] ~/nightshift state replay 2026-09-26 21:05Z and 21:45Z (BLOCKED loops, sys.exit(1) at supervisor.py:252); phantom #10 laps 213434/213853/214258 (retries 4→6) during restart races.

## L-010: a lap that crashes after `git push` leaves a divergent remote branch — every retry then crashes non-fast-forward with zero fair attempts
- What happened: #12's first lap pushed agent/issue-12 then crashed at the merge identity check; worktree_for() rebuilds the local branch from origin/main with `-B`, so the retry's history diverged from the stale remote tip and `git push -u origin agent/issue-12` was rejected non-fast-forward — crashing before any model output was judged. Two consecutive strikes (210034, 210455) were pure instrument; #12 burned retries without a single fair attempt until the operator reset its counter.
- Why: agent/issue-<n> branches are factory-owned single-writer refs; the push sits before the merge gate, so any post-push crash re-poisons the next attempt. Force-push on owned refs is safe and deterministic.
- What changes in the product build: `push --force-with-lease` at the lap push site (factory-spike commit 558eb0a9); same rule for any future per-issue ref. Advisory Day-4 review had flagged --force-with-lease as future hardening; it is a proven in-run defect now.
- Evidence: state/evidence/20260926T210034-issue-12/verdict.json and 210455 (non-fast-forward errors); fix + reset → 212615 lap GREEN (PR #16).

## L-011: squash-merge identity is a real integrity gate — but merge and identity check must be atomic
- What happened: #12's first lap pushed and squash-merged (PR #15 landed on GitHub, merge commit 8935820a) BEFORE post_merge_identity() compared the merge tree to the verified head (66ec070c). The trees genuinely differed (the squash rode on top of c17d2641, i.e. #13's just-merged content; the branch head was based on e6b3db4) — the gate correctly refused to bless the merge as an identity-match, but the merge had already happened and the lap recorded crash. Net: correct stop, non-atomic sequence.
- Why: `gh pr merge --squash` applies the PR diff onto the CURRENT base, not onto the branch's parent; a branch based on a stale base produces a squash tree that legitimately differs from the verified head whenever main moved mid-lap. Tree equality between merge result and verified head is the right invariant; the error is executing the merge before proving the tree.
- What changes in the product build: before creating the PR, rebase/verify the branch against a fresh origin/main fetch (or assert merge-base == origin/main), so a mid-lap main move fails at a cheap pre-check instead of after a public merge; keep post_merge_identity as the loud backstop. The merged tree itself was behaviorally correct (live rig passes both oracles) — recorded as a caveat, not a false green.
- Evidence: PR #15 merge 8935820a vs head 66ec070c 6-line content diff (`count`/`/stats`); IdentityMismatch text in 204208-issue-12 verdict.json.

## L-012: issue lifecycle must be driven by the merge, never by human/model closure — and CLOSED ≠ merged
- What happened: pre-launch sanity found issue #9 CLOSED on GitHub while its scenario was RED against main (Day-4 parked it after 3 retries; something closed it without a merge). Day-5 relaunch nearly dispatched work against a "done" issue whose fix does not exist. Separately, the final supervisor exited with "queue blocked: issue 13" although #13 was merged+deployed — state.json kept disposition "retry" because the lap crashed post-close.
- Why: GitHub issue state is not evidence of landing; the durable disposition is. Conversely a closed issue with a non-terminal local disposition makes claim_next return None while the blocked-detector screams.
- What changes in the product build: (1) reconcile upgrades disposition to merged when the issue is closed AND its scenario passes on live main (or at minimum when a merge commit referencing it is on main); (2) closed-without-merge issues get reopened with a comment linking the RED scenario evidence; (3) BLOCKED detection treats "issue closed on GitHub" as terminal.
- Evidence: gh issue list (#9 CLOSED, scenario RED on e6b3db4 and on 9045492e main); supervisor-day5d BLOCKED exit 21:45:10Z.

## L-013: no dispatch-time RED re-check — a lap can be spent on an already-satisfied issue
- What happened: PR #15 (merge 8935820a) landed #12's DELETE behavior on main at 20:44Z, mid-incident, via the crashed first #12 lap. The two subsequent #12 laps (21:22Z failure, 21:26Z green) both "implemented" an issue that was already satisfied — refactor laps, not defect→fix attempts — and the 21:26Z green was recorded as an independent fix. Same class as L-012: issue lifecycle state driven by lap outcome, never re-validated against the repo.
- Why: dispatch selects an open GitHub issue, but nothing re-runs the issue's scenario (the RED oracle) against fresh main before spending a lap; a mid-incident merge (or any external landing) silently vacates the work the lap is about to do.
- What changes in the product build: at dispatch time, re-run the issue's scenario against a fresh origin/main checkout; if GREEN, reconcile the issue as merged (L-012's rule) and skip the lap. Keeps lap cost for genuine work only.
- Evidence: `git show 8935820a` (do_DELETE + PasteStore.delete, merged 20:44Z); claimed.diffs of 20260926T212214-issue-12 and 20260926T212615-issue-12 refactor already-present code; DAY5_REPORT.md fair-attempt accounting.

## L-014: apply ladder discards all but the last tier's stderr — the first-tier error is the diagnostic
- What happened: lap.apply_diff runs plain → --recount → --recount -C1 and, on total failure, records only the LAST tier's stderr (lap.py:253). All four #10 diff-apply failures recorded generic "patch does not apply @app.py:NN" (tier-2/3 context-search messages), hiding the tier-1 verdicts that replay recovered: "corrupt patch at line 88" (a new-file hunk count typo — 74 declared, 71 actual) and "patch fragment without header". Tier-1 stderr would have classified these instantly; the recorded text made the failures look like context misalignment, which the report initially over-trusted as "genuine model failure".
- Why: the tier that applied is the signal (implementer-quality metric), and symmetrically the tier that FIRST failed carries the structural diagnosis — a ladder must record every rung, not just the last.
- What changes in the product build: apply_diff records each tier's exit code + verbatim stderr in run evidence (tier_results list); verdict.json's error text quotes tier 1 on structural parse failures, the last tier only on context-search failures.
- Evidence: replay of all four #10 claimed.diffs at 9045492e (worktree reproduction, this correction pass); lap.py:235-253; DAY5_REPORT.md replay section.

## L-015: S1 is unmeasurable without an interventions log — manual actions were interventions and were never recorded
- What happened: the written S1 criterion (SPIKE_PROD.md:10) is 3 consecutive laps with zero human interventions. Day 5 involved manual `rm -f state/claims/*.json`, 5 supervisor kills/restarts, hand-written PID files, and a hand-reset of #12's retry accounting — every one an intervention under the written text — but `state/interventions.jsonl` does not exist, so none were recorded in-run. The probe as specified (dispatch count + empty interventions file) is vacuous when nothing writes the log; the S1 rescore had to be reconstructed after the fact from the operator's transcript.
- Why: an "unattended" criterion needs an instrumented definition of "touch": any manual state/claims edit, supervisor kill/restart, pid-file write, or retry-counter edit is an intervention, and the spike had no way to notice itself being touched.
- What changes in the product build: an append-only state/interventions.jsonl that reconcile() writes to whenever it observes artifacts inconsistent with recorded lap outcomes (orphan claims, pid mismatches, counter drift); S1's probe then measures something real. Recommendation alongside: keep the stricter all-greens bar (3 consecutive zero-touch GREEN laps) as the target, but score the written zero-interventions text honestly.
- Evidence: `test -f state/interventions.jsonl` → absent ([redacted-host] + migrated laptop copy); SPIKE_PROD.md:10; DAY5_REPORT.md S-score S1 row (rescored NOT MET).

## L-016: stale worktree registrations trap every retry — worktree creation must self-heal, and cleanup must not be skippable
- What happened: launch-3's erroneously dispatched-parked-17 lap (21:12Z) left its worktree registered at .factory/worktrees/agent-issue-17 and was never cleaned. Launch-5's #17 laps (run-ids 20260928T212724, 212948, 213213) then all crashed identically before any model output: `worktree add` died with "fatal: 'agent/issue-17' is already used by worktree at <path>", and because run() initialized `worktree = None` with the finally-guard `if worktree:`, a raise from worktree_for BEFORE assignment skipped the cleanup — so each crash re-created the trap for the next retry. Deterministic instrument failure: #17 would have parked at retries=3 with zero real model laps.
- Why: unattended runs cannot depend on operator cleanup between launches. A per-issue resource with a deterministic name needs two properties: creation that self-heals a leftover registration (remove --force + prune + exactly one retry, only on the collision signature), and a cleanup path that holds the deterministic path before the try, so the finally reaps even when creation raises. Foreign-worktree-on-branch and any other failure must still raise loud — the heal is signature-scoped, never a loop.
- What changes in the product build: `worktree_for`'s add path self-heals the registered-path collision (unit d1985399, factory-spike); `run()` pre-assigns the worktree path via the shared `_worktree_path` before the try so the finally always reaps (unit 5284986). Regression tests: real-git collision self-heal, foreign-worktree-on-branch still raises loud, unrecoverable failure still raises, worktree_for-raise still reaps the registration and records the crash.
- Evidence: state/evidence/20260928T212724/212948/213213-issue-17 verdict.json (identical worktree-add RuntimeError, outcome crash, gate null); `git worktree list` on the product repo showing the launch-3 registration at 5b7365b; launch-5 interventions.jsonl (aborted-launch5) rows 4/8 — crash/retry with zero gate sequence; launch-6 first #17 lap GREEN end-to-end past worktree_for (PR #23, merge f24f066, 47s wall) after the fix + disclosed operator cleanup of the stale registration.
